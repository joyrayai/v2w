# 合规审查平台 · 系统逻辑设计

> 版本：v0.1（逻辑设计稿）
> 范围：业务逻辑与系统逻辑设计。不包含网络安全相关内容。

---

## 0. 设计总纲

一句话：**一个引擎、一份策略、两种模式、三档处置、全程留痕。**

| 概念 | 含义 |
|---|---|
| 一个引擎 | 全公司只有一个合规审查引擎（无状态服务），所有入口调它 |
| 一份策略 | 规则只存在于策略中心，版本化；引擎运行时加载 |
| 两种模式 | `advisory`（预审，建议性，不阻断）/ `gate`（收束，权威，可阻断） |
| 三档处置 | `pass`（低风险自动放行）/ `review`（中风险人工复核）/ `block`（高风险拦截升级） |
| 全程留痕 | 每次审查（包括静默通过）都产生审计事件 |

## 1. 核心数据契约

所有接入面（openclaw skill、飞书、BPM、创作工具）与引擎之间，只通过以下三个契约通信。**契约稳定是整个平面的"普通话"。**

### 1.1 审查请求 ReviewRequest

```json
{
  "requestId": "req_8f2k3j",
  "mode": "advisory | gate",
  "scene": "marketing_material | rep_visit_plan | rep_visit_record | speaker_event | meeting_minutes | generic_doc",
  "subject": {
    "docId": "doc_a1b2c3",
    "version": 4,
    "contentHash": "sha256:...",
    "format": "text | docx | pdf | pptx | form",
    "title": "XX产品学术推广PPT",
    "content": "（解析后的纯文本/结构化内容）",
    "attachments": []
  },
  "context": {
    "submitterId": "u_123",
    "submitterRole": "marketing | rep | medical | other",
    "department": "市场部",
    "product": "注射用XX",
    "targetAudience": "HCP | patient | internal",
    "channel": "academic_meeting | visit | wechat | print | digital",
    "bpmInstanceId": "bpm_20260611_001"
  },
  "options": {
    "policyVersion": "latest | v2026.06.1",
    "deltaBase": "sha256:...",
    "timeoutMs": 30000
  }
}
```

要点：
- `scene` 决定加载哪组规则（场景化规则包），是路由的第一键。
- `contentHash` 是版本封存与增量审查的基础。
- `deltaBase` 可选：传上次已审版本的哈希，引擎只对差异部分做深度审查（提速、降本）。
- `gate` 模式必须携带 `bpmInstanceId`，保证判定与审批实例一一对应。

### 1.2 审查判定 ReviewVerdict（标准判定结果）

```json
{
  "verdictId": "vd_9x8y7z",
  "requestId": "req_8f2k3j",
  "mode": "gate",
  "riskLevel": "none | low | medium | high",
  "action": "pass | suggest | review | block",
  "policyVersion": "v2026.06.1",
  "findings": [
    {
      "findingId": "f_001",
      "ruleId": "MKT-OFFLABEL-001",
      "ruleTitle": "疑似超适应症宣传",
      "severity": "high",
      "engine": "llm | rule | hybrid",
      "confidence": 0.92,
      "location": { "page": 5, "paragraph": 2, "quote": "对XX症状同样有效" },
      "rationale": "该表述涉及的适应症未在批准说明书范围内",
      "evidence": [
        { "type": "label", "ref": "XX说明书 v2025-03 · 适应症章节", "uri": "kb://label/xx/2025-03#indications" }
      ],
      "suggestion": "删除该表述，或改为已批准适应症范围内的表述：……"
    }
  ],
  "summary": "共发现 1 处高风险、2 处低风险问题",
  "sealToken": null,
  "reviewedAt": "2026-06-11T10:32:00+08:00",
  "elapsedMs": 8400
}
```

要点：
- `riskLevel` 是整体等级（聚合后），`findings[].severity` 是单条等级。
- 每条 finding 必须带 `location`（能定位到原文）、`rationale`（为什么）、`evidence`（依据什么）、`suggestion`（怎么改）。**四要素缺一不可**，否则业务侧无法整改、合规侧无法辩护。
- `sealToken`：仅 `gate` 模式且 `action=pass` 时签发（见 §5 封版逻辑）。

### 1.3 审计事件 AuditEvent

```json
{
  "eventId": "ev_...",
  "eventType": "review_requested | verdict_issued | human_decision | seal_issued | seal_verified | seal_mismatch | policy_changed | appeal_filed | appeal_resolved",
  "occurredAt": "...",
  "actor": { "type": "user | system | agent", "id": "u_123" },
  "subject": { "docId": "...", "version": 4, "contentHash": "..." },
  "payload": { "verdictId": "...", "riskLevel": "high", "decision": "override_release", "reason": "医学部确认该表述有最新批件支持" },
  "policyVersion": "v2026.06.1"
}
```

要点：
- 审计事件**只追加、不修改**（append-only）。
- 人工改判（override）必须填 `reason`，且事件记录改判人。

## 2. 审查引擎流水线逻辑

引擎内部为固定七段流水线，所有模式共用：

```
接收 → 解析 → 路由 → 规则引擎 → LLM 判定 → 聚合分级 → 出具判定
```

### 2.1 各段逻辑

1. **接收（Intake）**
   - 校验契约完整性；`gate` 模式校验 `bpmInstanceId` 存在。
   - 幂等：相同 `contentHash + scene + mode + policyVersion` 的请求直接返回缓存判定（见 §2.4）。

2. **解析（Parse）**
   - docx/pdf/pptx → 结构化文本（保留页码/段落定位信息，供 finding 定位）。
   - 表单类（拜访计划）→ 字段级结构。
   - 解析失败 → 返回 `action=review`（解析不了的东西不能默认放行）。

3. **路由（Route）**
   - 按 `scene` 加载对应规则包；按 `product` 加载对应说明书与产品红线。
   - 输出"本次适用规则清单"，写入判定（可解释性的一部分）。

4. **规则引擎（确定性检查）**
   - 处理所有可确定判断的规则：必备要素缺失（如安全性信息、批准文号）、禁用词、限额数值（讲者费、餐费）、必填字段、黑名单机构/人员匹配。
   - 输出带 `engine=rule, confidence=1.0` 的 findings。

5. **LLM 判定（语义检查）**
   - 处理语义类规则：超适应症暗示、疗效夸大、与竞品对比贬低、隐性利益输送表述、数据引用与原文不符。
   - 每条语义规则是一个独立的判定任务（规则 → 判定 prompt 模板 + 知识库引用），输出结构化 finding。
   - LLM 输出必须含 `confidence`；低置信度的处理见 §3.2。

6. **聚合分级（Aggregate）**
   - 按 §3 的分级逻辑把 findings 聚合为整体 `riskLevel` 与 `action`。

7. **出具判定（Issue）**
   - 写审计事件 `verdict_issued`；`gate+pass` 时签发 `sealToken`。

### 2.2 模式差异（仅两处）

| 差异点 | advisory 预审 | gate 收束 |
|---|---|---|
| action 映射 | 不产生 `block`，高风险也只是强提示（`review` 语义=“建议找合规”） | 完整三档处置，`block` 真实阻断 |
| 浮现策略 | `none/low` 完全静默；`medium+` 才浮现 | 全部回写 BPM |

引擎内部逻辑完全一致，**只在最后的 action 映射和输出渠道上分叉**。这保证两道防线永远口径一致。

### 2.3 同步 / 异步

- 预审（advisory）：同步优先，目标 P95 < 10s（编辑器内体验）。超时返回 `pending` + 回调。
- 收束（gate）：一律异步。BPM 提交后节点置"审查中"，引擎回调更新（见 §6 时序）。
- 长文档（>50 页 PPT/PDF）：自动转异步 + 分片并行审查 + 聚合。

### 2.4 缓存与增量

- **判定缓存**：`(contentHash, scene, mode, policyVersion)` 四元组命中即返回。文档没改、策略没变，不重复消耗。
- **增量审查**：携带 `deltaBase` 时，规则引擎全量跑（便宜），LLM 仅对 diff 段落跑，未变段落继承上次 findings。
- **缓存失效**：策略中心发布新版本 → 按规则包影响范围使相关场景缓存失效。

## 3. 风险分级逻辑

### 3.1 聚合规则（决策表）

整体 `riskLevel` 由 findings 聚合，**取最严原则 + 数量升级**：

| 条件 | 整体等级 |
|---|---|
| 存在任一 `high` finding | `high` |
| 无 high，存在任一 `medium` | `medium` |
| 无 high/medium，`low` 数量 ≥ N（默认 5） | `medium`（量变引质变） |
| 仅少量 `low` | `low` |
| 无 finding | `none` |

`action` 映射（gate 模式）：

| riskLevel | action | 处置 |
|---|---|---|
| none / low | `pass` | 自动放行 + 签发封版令牌 + 静默留痕 |
| medium | `review` | 派单合规专员，附 findings 与建议 |
| high | `block` | 阻断 + 自动升级（见 §6.3） |

### 3.2 置信度处理（LLM finding 专用）

| confidence | severity=high 的处理 | severity=medium/low 的处理 |
|---|---|---|
| ≥ 0.85 | 按 high 生效 | 按原级生效 |
| 0.6 ~ 0.85 | 降为 medium（
